RMS — Remote Monitoring System

← Back to Index

Definition & Overview

A Remote Monitoring System (RMS) is a centralized platform that enables network engineers to monitor, manage, and troubleshoot network devices — routers, switches, firewalls, access points — without requiring physical access to the equipment. For an ISP like Matrix Telecom, RMS is not a luxury but a necessity: the network spans the entire city of Yaoundé and beyond, and dispatching a technician to every site for routine checks or simple fixes would be prohibitively expensive and slow.

An RMS combines several capabilities into one system: device discovery and inventory, real-time monitoring via SNMP/ping, remote CLI access (SSH/Telnet) through a secured jump host, configuration backup/restore, firmware management, and out-of-band management (OOBM) for devices that lose primary connectivity. It is the single pane of glass from which the NOC team operates.

How It Works — Technical Deep Dive

1. Agentless vs. Agent-Based Monitoring

Most RMS platforms support both models:

  • Agentless: The RMS communicates with devices using standard protocols (SNMP, ICMP, SSH, Telnet, HTTP). No software is installed on the target device. This is preferred for routers, switches, and firewalls where installing an agent is not possible or undesirable.
  • Agent-Based: A small software agent is installed on servers (Windows/Linux) to collect detailed OS-level metrics — process list, disk I/O, application logs. Common agents include SolarWinds Agent, Zabbix agent, and PRTG Remote Probe.

2. Out-of-Band Management (OOBM)

OOBM is a critical component of RMS that ensures management access even when the production network is down. Methods include:

  • Dedicated management VLAN: A separate Layer 3 domain with private IPs (10.x.x.x) that carries only management traffic. This VLAN is separate from client data traffic.
  • LTE/4G Backup: The CPE or router has a cellular modem that provides a backup management path when the primary fiber or copper link fails.
  • Console Servers: Hardware devices (e.g., OpenGear, Raritan) that aggregate serial console ports from multiple routers. Engineers SSH into the console server and select the port corresponding to the target device, providing console-level access even if the network stack is non-functional.
  • BMC/iLO/iDRAC: For servers, the Baseboard Management Controller provides serial-over-LAN, remote power control, and virtual media — all accessible via dedicated management NIC on the OOBM VLAN.

3. Session Management and Auditing

RMS platforms typically provide a web-based SSH/Telnet client or integrate with a bastion/jump host. All sessions are logged: who accessed which device, at what time, and what commands were executed. This audit trail is essential for compliance (e.g., PCI-DSS, ISO 27001) and for incident postmortems.

4. Configuration Backup and Compliance

The RMS automatically backs up device configurations at scheduled intervals (nightly, weekly). Configurations are stored in version control (e.g., Git or the RMS's internal database). Engineers can compare configurations between backups, roll back to a known-good configuration after a failed change, and audit configuration drift over time.

5. Automated Workflows

Advanced RMS platforms support automation: when an alarm fires, the RMS can execute a pre-defined remediation script (e.g., bounce a port, restart a service, change a routing parameter). This reduces the mean time to repair (MTTR) for common issues like a stuck BGP session or a hung interface.

Practical Example at Matrix Telecom Yaoundé

Matrix Context: Which RMS Platform Does Matrix Use? Ask the Engineers!

Important: Before diving into this topic, ask your supervisor or a senior NOC engineer: "What RMS platform does Matrix Telecom use? Is it SolarWinds RMS, a custom solution, or something else?" The specific tool may vary, but the concepts in this page are universal.

At Matrix, the RMS is used daily for:

  • Monitoring core infrastructure: The two upstream routers (one in Douala, one in Yaoundé) are polled every 60 seconds via ICMP and SNMP. If either goes down, the RMS sends an SMS to the on-call engineer within 2 minutes.
  • Client CPE management: Each of the 400+ active client CPEs is accessible via SSH through the RMS jump host. When a client calls to report slow internet, the NOC engineer SSHes into the CPE, checks bandwidth usage, interface errors, and signal strength without leaving the Yaoundé office.
  • Configuration backup: Every night at 02:00, the RMS connects to every managed device, downloads the running configuration, and stores it in a versioned archive. If a configuration change breaks a client link, engineers can quickly roll back to the previous night's backup.
  • Power cycling: Some CPEs are connected to intelligent PDUs (Power Distribution Units). Through the RMS, engineers can remotely power-cycle a stuck CPE without needing a site visit.

Tools Used

RMS Web UI
Access: Typically https://rms.matrixtelecom.local (internal network)
Purpose: The primary interface for day-to-day monitoring and management
Common pages:
  • Dashboard: Shows overall network health — number of devices up/down, active alarms, interface utilization top-N.
  • Device Inventory: Searchable list of all managed devices with model, firmware, location, and status.
  • Remote Console: Built-in SSH/HTTPS launcher. Select a device, click "Connect", and get a terminal session instantly.
  • Backup Manager: View configuration backup history, compare revisions, and restore.
  • Reports: Scheduled reports on uptime, SLA compliance, and bandwidth trends.
SSH / Telnet
Purpose: Direct CLI access to devices for detailed troubleshooting
Usage: 
# Direct SSH to a device on the management VLAN
ssh noc-admin@10.200.10.1

# SSH via the RMS bastion host (jump box)
ssh -J noc@bastion.matrixtelecom.cm noc-admin@10.200.10.1

# Use SSH key pairs for passwordless access
ssh-keygen -t ed25519 -f ~/.ssh/matrix_rms_key
ssh-copy-id -i ~/.ssh/matrix_rms_key noc-admin@10.200.10.1

# Telnet (only on isolated OOBM networks, no encryption)
telnet 10.200.10.1 23
SNMP for Health Checks
Purpose: Quick health checks from the command line without the full RMS
Common commands: 
# Check device uptime
snmpget -v2c -c matrix_ro 10.200.10.1 1.3.6.1.2.1.1.3.0

# List all interfaces
snmpwalk -v2c -c matrix_ro 10.200.10.1 1.3.6.1.2.1.2.2.1.2

# Check interface operational status
snmpwalk -v2c -c matrix_ro 10.200.10.1 1.3.6.1.2.1.2.2.1.8

# Get interface bandwidth utilization (ifHCInOctets, 64-bit counter)
snmpwalk -v2c -c matrix_ro 10.200.10.1 1.3.6.1.2.1.31.1.1.1.6
Console Server (e.g., OpenGear)
Purpose: Serial console access to routers when SSH/SNMP is unavailable
Usage: 
# SSH to the console server
ssh admin@console-server.matrixtelecom.local

# List ports and their connected devices
show port-summary

# Connect to port 8 (connected to Core-RTR-Yaounde console port)
connect port 8
# You now have serial console access to Core-RTR-Yaounde
# This works even if the router's network stack has crashed

Common RMS Platforms at ISPs

  • SolarWinds RMS: Integrated with Orion. Provides remote desktop, SSH console, power management, and configuration backup.
  • Zabbix (with automated actions): Open-source. Can trigger remote commands via SSH on alert conditions.
  • PRTG (with probes): Distributed monitoring with remote probes that can be placed at each PoP for local monitoring continuity.
  • ManageEngine OpManager: Commercial. Good mid-range solution with integrated remote control.
  • OpenGear Console Servers + LibreNMS: Hardware console servers combined with an open-source monitoring platform.
  • Custom Bastion + Monitoring: A hardened Linux VM with SSH access to all management IPs, combined with Nagios/Icinga for alerts.

Tips for the Intern

Intern Tip:
  • Find out what Matrix uses: Ask the NOC team "What is our RMS?" and "Can I get a demo account to explore?" Understanding the specific RMS is a top priority.
  • Master SSH: You will SSH into devices constantly. Practice using SSH keys, config files, jump hosts, port forwarding, and ProxyJump.
  • Learn the management IP scheme: Matrix likely uses a consistent scheme like 10.200.x.x for management IPs. Knowing the scheme makes it easy to reach any device.
  • Always verify remote access: After a new CPE is installed, immediately SSH into it from the NOC to verify remote management works before the technician leaves the site.
  • Understand in-band vs. out-of-band: If you manage a device through its production-facing IP, it's in-band. Through a dedicated management port/VLAN, it's out-of-band. Know the difference.
  • Keep a session log: When troubleshooting, save your SSH session to a file. The exact commands and outputs you ran are invaluable for post-incident reports.
  • Ask about console servers: If Matrix uses them, ask for a tour of the rack. Understanding how serial console cabling works is rare knowledge that impresses interviewers.
  • Automate config backups: Even if the RMS does it, write a small Python/Bash script that does the same for your lab devices. Understanding the backup/restore process deeply is crucial.

Security Best Practices for RMS

  • Place management interfaces on a dedicated, isolated VLAN with strict ACLs.
  • Use SSH keys instead of passwords. Disable password-based SSH on all devices.
  • Use SNMPv3 with authentication and encryption (authPriv) when possible.
  • Enable MFA (multi-factor authentication) for RMS web UI logins.
  • Log and audit all remote sessions. Know who accessed which device and when.
  • Use a bastion/jump host: never expose management IPs directly to the internet.
  • Rotate SNMP community strings and SSH keys quarterly.
  • Document the RMS architecture and access procedures in a wiki.

Device Onboarding Checklist for RMS

  1. Assign a unique management IP from the OOBM VLAN range (e.g., 10.200.x.x/24).
  2. Configure the management interface in a dedicated VRF (if supported) or at minimum restrict ACLs to NOC source IPs.
  3. Enable SNMP with a restricted read-only community and limit to RMS IP.
  4. Enable SSH with key-based authentication.
  5. Configure NTP — accurate timestamps are essential for correlating logs.
  6. Forward Syslog to the central Syslog server (a component of RMS).
  7. Add the device to the RMS inventory with all fields (serial, model, firmware, location).
  8. Run an initial configuration backup in the RMS.
  9. Test remote SSH access through the RMS jump host.
  10. Verify SNMP data appears in the RMS dashboard (CPU, memory, interfaces).

Troubleshooting Remote Access Issues

Problem: Cannot SSH to device 10.200.10.1
Checklist:
  [ ] Can you ping 10.200.10.1? If no, check OOBM connectivity.
  [ ] Is SSH port open? nmap -p 22 10.200.10.1
  [ ] Does the device have a default route in the management VRF?
  [ ] Are there ACLs blocking SSH from the NOC subnet?
  [ ] Is the device powered on? (check UPS status via OOBM if available)
  [ ] Is the SSH service running? (check with console server if accessible)
  [ ] If all else fails, lodge a site visit request.
