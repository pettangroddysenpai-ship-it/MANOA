PRTG Network Monitor (Paessler)

Definition & Overview

PRTG (Paessler Router Traffic Grapher) is an all-in-one network monitoring solution developed by Paessler AG. It is designed to be easy to set up and operate while still providing deep monitoring capabilities. PRTG uses a sensor-based architecture where each metric being monitored is represented as an individual sensor. A single device (e.g., a router) is monitored by multiple sensors: one for ping, one for CPU load, one for each interface's bandwidth, one for memory, and so on.

For an ISP like Matrix Telecom, PRTG offers a compelling balance of ease of use and power. It supports auto-discovery via SNMP scans, integrated alerting (email, SMS, push notifications), customizable dashboards, map views, and distributed monitoring via remote probes. The freeware edition supports up to 100 sensors — enough to monitor a small network. Larger deployments require a commercial license.

How It Works — Technical Deep Dive

1. Sensor-Based Architecture

In PRTG, everything is a sensor. A sensor is a monitoring component that collects a specific metric from a device. PRTG includes over 200 pre-built sensor types:

  • Ping Sensor (ICMP): Checks device availability and response time.
  • SNMP Traffic Sensor: Monitors interface bandwidth using ifHCInOctets/ifHCOutOctets.
  • SNMP CPU Load Sensor: Monitors CPU utilization hrProcessorLoad.
  • SNMP Memory Sensor: Monitors memory usage (hrStorageUsed).
  • HTTP Sensor: Checks if a website is responding and optionally validates content.
  • Port Sensor: Checks if a specific TCP port is open (e.g., port 22 for SSH).
  • WMI Sensor: Monitors Windows servers using WMI.
  • SSH Script Sensor: Executes a script on a Linux device via SSH and parses the output.
  • NetFlow / sFlow / IPFIX Sensor: Collects flow data for traffic analysis by application and conversation.

2. Auto-Discovery

PRTG's auto-discovery feature scans an IP range using SNMP. It identifies each device, determines its type (router, switch, server, printer), and automatically creates the appropriate sensors. For example, for a router, PRTG creates a Ping sensor, SNMP system health sensors (CPU, memory), and an SNMP Traffic sensor for each active interface. This drastically reduces setup time.

3. Monitoring Core (Server) and Remote Probes

PRTG follows a client-server architecture:

  • PRTG Core Server: The central server that manages configuration, stores data in an internal database, and hosts the web interface. Runs on Windows.
  • Remote Probes: Lightweight agents deployed at remote sites (e.g., the Douala PoP). The probe collects data locally and sends it back to the core server. If the WAN link to the core goes down, the probe caches data and forwards it when connectivity is restored.

4. Alerting and Notifications

PRTG's notification system is flexible and supports:

  • Email (SMTP)
  • SMS (via email-to-SMS or HTTP gateway)
  • Push Notifications (PRTG mobile app)
  • Slack / Microsoft Teams / Discord webhooks
  • Execute a program or script
  • Syslog message
  • SNMP trap

Each sensor can have multiple triggers: "up" to "down" transition, threshold exceeded, and recovery.

5. Dashboards and Maps

PRTG provides a drag-and-drop dashboard editor. Users can create custom dashboards with gauges, graphs, tables, and maps. The "PRTG Maps" feature allows drawing network topology diagrams with live status indicators — green for up, red for down.

Practical Example at Matrix Telecom Yaoundé

Matrix Context: Real-Time Monitoring of All Network Equipment

If Matrix Telecom uses PRTG (or a similar tool), the NOC team relies on it for real-time visibility into the entire network. Here is a typical PRTG setup:

  • Core Routers: Two core routers (Yaoundé and Douala) each have 15–20 sensors: Ping (100ms interval), CPU load, memory usage, temperature (if available via SNMP), and one traffic sensor per interface (WAN, client aggregation, internal backbone).
  • Client CPEs: Each active CPE has a minimum of 4 sensors: Ping, SNMP Traffic on the WAN interface, SNMP Traffic on the LAN interface, and a custom sensor for signal strength (SNR) if wireless. That is 1600 sensors for 400 CPEs — easily within a commercial PRTG license.
  • Server Infrastructure: The RADIUS server, DHCP server, DNS resolver, and billing server each have HTTP/HTTPS sensors checking service availability, plus WMI sensors for disk space and memory.
  • Alerts: When a core router's WAN interface exceeds 90% utilization, PRTG sends a push notification to the NOC engineer's mobile phone. When a client CPE's ping sensor goes down, PRTG escalates: email within 5 minutes, SMS to the on-call engineer after 15 minutes if unacknowledged.

Sensor Configuration Example: Monitoring a Router

Adding a Router to PRTG

  1. Open the PRTG web interface (http://prtg.matrixtelecom.local or https://prtg.paessler.com).
  2. Go to Devices > Add Device.
  3. Enter:
    • Device Name: "Core-RTR-Yaounde"
    • IP Address/DNS Name: "10.200.10.1"
    • SNMP Community (v2c): "matrix_ro"
  4. Click Add Device. PRTG runs auto-discovery and suggests sensors.
  5. Check the following sensors to create:
    • Ping — availability, response time, packet loss
    • SNMP CPU Load — 5 seconds average, 1 minute average
    • SNMP Memory — percent used
    • SNMP Traffic — for each interface: WAN (1 Gbps), LAN Aggregation (1 Gbps), Management (100 Mbps)
    • SNMP Uptime — device uptime in days
  6. Click Create Sensors. PRTG begins polling immediately.
  7. Configure alert thresholds:
    • Ping: Down if >5 consecutive timeouts, trigger email to NOC
    • CPU: Warning at 80%, Critical at 95%, trigger push notification
    • Traffic on WAN: Warning at 80% (800 Mbps), Critical at 95% (950 Mbps)

Tips for the Intern

Intern Tip:
  • Is PRTG used at Matrix? Ask the NOC team. If not, the concepts here (sensors, SNMP, auto-discovery, notifications) transfer directly to whatever tool they use.
  • Start with the freeware edition: The 100-sensor free version is perfect for learning. Install it on a VM, add your home router, and practice configuring sensors and alerts.
  • Learn the sensor types: PRTG has over 200 sensor types. Spend an afternoon browsing the "Add Sensor" menu to understand what's available.
  • Use the "Auto-Discovery" feature: When you add a device, let PRTG auto-discover sensors before creating them manually. It often finds metrics you didn't think to monitor.
  • Create a meaningful dashboard: Add the most important sensors (core routers, DNS, DHCP) to the default dashboard. NOC staff should see the network's pulse at a glance.
  • Set up test notifications: After configuring a notification trigger, use the "Test Notification" button to verify email/SMS/push works before relying on it during an actual outage.
  • Understand sensor limits: 1 device = multiple sensors. A router with 8 interfaces can easily consume 10+ sensors. Plan your license accordingly.
  • Use dependencies: If a switch is down, all devices behind it will appear down too. Configure parent-child dependencies so PRTG only alerts on the root cause (the switch), not the downstream devices.

Best Practices for PRTG at an ISP

  • Group devices by location: Create groups for each city (Yaoundé, Douala, Bafoussam) and within each group, subgroups for Core, Client CPEs, and Infrastructure.
  • Set appropriate polling intervals: Core infrastructure: 60 seconds. Client CPEs: 300 seconds. Reduce overhead by increasing intervals for less critical devices.
  • Use maintenance windows: When upgrading firmware on a router, schedule a maintenance window in PRTG to suppress alerts during the reboot.
  • Monitor the core server: Create sensors that monitor the PRTG server's own disk space, memory, and database size.
  • Regularly review sensor health: Disable or delete sensors that are no longer relevant (decommissioned devices, removed interfaces). Dead sensors clutter the interface and waste polling resources.
  • Backup the PRTG configuration: Settings > System Backup. Schedule automatic backups to a network share.

Comparing PRTG to Other Tools

  • PRTG vs. SolarWinds: PRTG is easier to set up and has a lower price point. SolarWinds is more scalable for very large enterprises (10,000+ devices).
  • PRTG vs. Cacti: PRTG has built-in alerting and a modern UI; Cacti has superior long-term graphing with RRDTool but no native alerts.
  • PRTG vs. Zabbix: Zabbix is open-source and more flexible but has a steeper learning curve. PRTG is more GUI-driven and staff-friendly.
  • PRTG vs. LibreNMS: LibreNMS is open-source but requires Linux administration skills. PRTG runs on Windows and is easier for non-Linux teams.
