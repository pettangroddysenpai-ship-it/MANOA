IPPLAN — IP Address Management (IPAM)

Definition & Overview

IP Address Management (IPAM) is the systematic process of planning, tracking, and managing IP address space and subnets within a network. For an ISP like Matrix Telecom in Yaoundé, effective IPAM is essential for avoiding IP conflicts, ensuring efficient use of allocated address blocks, and providing accurate documentation for troubleshooting and auditing. An IPPLAN (IP Plan) is the concrete document or software tool that records every subnet allocation, VLAN assignment, and device IP across the entire network.

Without a reliable IPPLAN, Matrix's engineers would struggle to know which IP blocks are assigned to which client, where free space exists for new clients, and which subnets belong to which region or service type. This leads to wasted IP space, duplicate allocations, and prolonged outage resolution times.

How IPAM Works — Technical Deep Dive

Hierarchical IP Space Organization

An IPAM system organizes the allocated IP space (obtained from AFRINIC for Cameroon providers, typically a /20 or larger block) into a hierarchical tree of subnets. Each subnet is characterized by its CIDR notation (e.g., 196.168.50.0/28), its purpose (client link, infrastructure, management), and its geographical or functional location. Subnets are further subdivided into smaller blocks for point-to-point links (/30), client LANs (/28 or /24), and internal infrastructure (/24).

Lifecycle of an IP Allocation

  1. Request: An engineer or sales agent identifies a need for IP space (new client, new PoP, internal server).
  2. Reservation: The IPAM admin reserves a block in the tool, marking it with the client name, contact, and requested subnet size.
  3. Allocation: The specific subnet is assigned from the appropriate pool (e.g., "Douala Client Subnets"). The gateway, first/last usable IP, and broadcast address are calculated and recorded.
  4. Assignment: Individual IPs are assigned to specific network interfaces — CPE WAN IP, CPE LAN subnet, management IP, loopback, etc.
  5. Monitoring & Reconciliation: The monitoring system (SolarWinds/PRTG/Cacti) polls the assigned IPs. Periodic scans (nmap, arp-scan) detect unrecorded devices and flag discrepancies.
  6. Reclamation: When a client disconnects, the IP block is deallocated in the IPAM and returned to the free pool, potentially after a quarantine period.

VLAN-to-Subnet Mapping

A robust IPPLAN also maintains a 1:1 mapping between VLAN IDs and IP subnets. For example, VLAN 100 corresponds to subnet 196.168.100.0/24 and is described as "Bastos Business Clients." This prevents overlapping subnets across access switches and simplifies troubleshooting when tracing a client port to its subnet.

Practical Example at Matrix Telecom Yaoundé

Matrix Context: Managing IP Allocations for All Clients – Tracking Which IP Is Assigned to Which CPE

At Matrix Telecom, each new business client requires at minimum three IP allocations:

  1. A management IP (often from a 10.x.x.x/8 private range) assigned to the CPE's bridge or loopback interface for remote monitoring (ping, SNMP, SSH).
  2. A public /30 (or private /30 if using CGNAT) for the WAN link from Matrix's aggregation router to the CPE.
  3. A private LAN subnet for the client's internal network (typically /28 or /24, depending on client size).

These allocations are recorded in the IPAM with the client name, CPE serial number, CPE model, installation date, and circuit ID. Without accurate IPAM records, an engineer troubleshooting a client outage would have to manually trace cables, ping sweep subnets, or guess which IP corresponds to which client — wasting valuable time during an active outage.

Tools Used

PHPIPAM — Open Source IPAM
Type: Web-based IPAM application (free, self-hosted)
Access: Usually at http://ipam.matrixtelecom.local or http://phpipam.matrixtelecom.cm
Features:
  • Organize IP space into sections (e.g., Yaoundé, Douala, Infrastructure, Clients)
  • Add subnets and automatically calculate CIDR, usable range, and utilization
  • Assign individual IPs to devices with hostname, owner, and notes
  • Subnet visualization — color-coded utilization bar
  • VLAN management with 802.1q ID tracking
  • Import/export via CSV for bulk operations
  • Permission-based access (read-only for interns, admin for NOC)
Usage steps for adding a subnet:
  1. Log into PHPIPAM
  2. Navigate to the appropriate section (e.g., Yaoundé > Client Subnets)
  3. Click "Add subnet" and enter the CIDR
  4. Fill in description, VLAN ID, and tags
  5. Click "Create"
Excel / Google Sheets — Simple IP Tracking
Type: Spreadsheet-based IPAM (used when dedicated software is not available)
Typical column layout:
Subnet (CIDR) | Client Name | Site | CPE Model | CPE Serial | WAN IP | Gateway | VLAN | Status | Date Assigned
Caveats: Excel lacks validation (two people can assign the same IP), concurrent editing, and subnet auto-calculation. It is a useful starting point but should be replaced by PHPIPAM or NetBox as soon as practical.
Pro tip for interns: If Matrix uses Excel for IPAM, volunteer to migrate it to PHPIPAM — it's a valuable project for your internship portfolio.
NetBox — Advanced IPAM + DCIM
Type: Open-source IPAM and Data Center Infrastructure Management
Features: In addition to PHPIPAM capabilities, NetBox tracks devices, racks, cables, circuit terminations, power panels, and much more. It is the de facto standard for serious ISP IPAM implementations.
Access: Often at http://netbox.matrixtelecom.local
Usage: NetBox uses a "prefix" (subnet) and "IP address" model. Prefixes can be hierarchical (parent/child). Each device can have multiple IPs assigned to its interfaces.

How to Avoid IP Conflicts

IP conflicts (two devices on the same subnet with the same IP) cause one or both devices to lose connectivity. Common causes at an ISP include:

  • Two engineers simultaneously allocating the same /30 from an outdated Excel sheet
  • Forgotten devices (decommissioned CPEs) still powered on and claiming an IP
  • DHCP scope overlapping with static assignments
  • Duplicate DHCP servers configured accidentally

Mitigation strategies:

  • Use an IPAM tool (PHPIPAM/NetBox) as the single source of truth — always check before assigning
  • Enable DHCP snooping on access switches to block rogue DHCP servers
  • Run weekly IP scans (nmap -sn 196.168.0.0/16) and reconcile with IPAM records
  • Use arp-scan to detect active IPs not in the IPAM: arp-scan --interface=eth0 196.168.50.0/24
  • In case of a conflict, disconnect the offending device, change its IP, then reconnect

Tips for the Intern

Intern Tip:
  • Memorize the CIDR chart (especially /24, /28, /29, /30). You will calculate subnets daily.
  • Ask first, assign second: Always check with a senior engineer before allocating a new subnet. There may be reserved blocks you don't know about.
  • Document everything: If you assign an IP, immediately update the IPAM. "I'll do it later" leads to lost IPs and conflicts.
  • Use ping sweeps to verify: Before assigning a block, run nmap -sn to confirm it's truly empty.
  • Learn the IPAM tool of choice at Matrix: If they use PHPIPAM, learn its API. If NetBox, learn the REST API. Automating IP allocations is a superpower.
  • Understand private vs. public IP space: Matrix likely uses 10.0.0.0/8 for internal management, and AFRINIC-allocated public IPs for client subnets and BGP announcements.
  • Keep a subnet cheat sheet pinned: Print the CIDR table above and tape it to your monitor.
  • IPv6 is coming: Even if Matrix hasn't deployed IPv6 yet, learn the IPv6 subnetting model (/64 per subnet, /48 per site). AFRINIC encourages IPv6 adoption.

Exercise

Task 1: Design a Subnet Scheme for a New Matrix Office Site

Matrix Telecom is opening a new branch in Douala with 3 departments (Sales: 30 hosts, NOC: 50 hosts, Admin: 20 hosts) plus a management network (10 hosts) and a guest Wi-Fi (100 hosts). You must plan the IP addressing using the 10.20.0.0/16 block. This exercise simulates the daily IPAM work a network engineer performs when onboarding a new site.

  1. Determine the smallest subnet (prefix length) that fits each department's host requirement plus 20% growth margin.
  2. Allocate subnets sequentially from 10.20.0.0/16: Sales first, then NOC, Admin, Management, Guest.
  3. Document each subnet in the IPAM tool (or a spreadsheet) with: subnet ID, gateway (first usable IP), VLAN ID, and purpose.
  4. Verify no overlapping ranges using a subnet calculator (e.g., ipcalc 10.20.0.0/24 on Linux).
  5. Define a routing summary: can all subnets be summarized as 10.20.0.0/20? Show the calculation.
  6. Add a comment in the IPAM for each block with the site name and contact person.

Task 2: Perform an IP Address Audit with Ping Sweep

Before deploying new equipment at a client site, you must verify that the planned IP range is actually unused. At Matrix, conflicts caused by overlapping private IP assignments can bring down a customer's network. This task teaches you to audit a subnet before allocation using standard CLI tools.

  1. Given a candidate subnet 192.168.50.0/24, run nmap -sn 192.168.50.0/24 from a Linux jump host in the NOC.
  2. Record all responding IPs, their MAC addresses, and any reverse DNS names.
  3. Cross-reference the discovered IPs against the IPAM database — flag any that are not documented.
  4. If a conflict is found (IP in IPAM but responding to ping from a different MAC), escalate to the senior engineer.
  5. Update the IPAM with the audit results and add a note "Last audited: [date]".

IP Planning Best Practices

  • Allocate IP blocks hierarchically to enable route summarization. Group subnets by region, then by client type.
  • Leave 10–20% free space in every subnet for future growth. Do not allocate 100% of a /24.
  • Standardize on /30 (not /31) for point-to-point links unless all equipment supports RFC 3021.
  • Use private IP space (10.x.x.x/8) for all management and infrastructure; reserve public IPs for client-facing allocations and BGP.
  • Define a naming convention for subnets: e.g., "CM-NS-YDE-INFRA-01" (Cameroon, Network Services, Yaoundé, Infrastructure, index).
  • Document every subnet with VLAN ID, switch port, gateway IP, and responsible engineer's contact.
  • Reconcile IPAM with actual network state every quarter via automated scanning.
