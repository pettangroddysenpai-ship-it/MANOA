SolarWinds — Enterprise Network Monitoring Platform

← Back to Index

Definition & Overview

SolarWinds is a comprehensive enterprise-grade network monitoring and management platform widely adopted by ISPs, telecom operators, and large enterprises. It provides deep visibility into network infrastructure through SNMP polling, flow analysis, alerting, performance monitoring, and network topology mapping. The platform is modular, built on the Orion framework, allowing organizations to purchase and deploy only the modules they need.

At Matrix Telecom Yaoundé, SolarWinds (or similar Orion-based tools) can be used to monitor the health and performance of core routers, switches, firewalls, and client CPEs across the network. The platform's ability to poll thousands of devices from a single console makes it ideal for an ISP managing a growing base of residential and business clients.

SolarWinds uses SNMP (Simple Network Management Protocol) to collect data from network devices, stores historical performance data in a SQL database, and presents it through a web-based dashboard with customizable views, alerts, and reports.

How It Works — Technical Deep Dive

1. SNMP Polling Engine

SolarWinds uses a polling engine that sends SNMP GET requests to monitored devices at configurable intervals (typically every 5 minutes). The engine collects data from OIDs (Object Identifiers) defined in MIBs (Management Information Bases). For example, interface bandwidth utilization is derived from the ifInOctets and ifOutOctets OIDs (1.3.6.1.2.1.2.2.1.10 and 1.3.6.1.2.1.2.2.1.16).

The polling engine stores collected data in the Orion database (SQL Server). SolarWinds calculates delta values between polls to compute utilization percentages, then renders these as line graphs in the web console.

2. Alerting Engine

SolarWinds includes a sophisticated alerting engine that triggers actions based on thresholds. Alerts can be configured for:

  • Interface down/discarding packets
  • High CPU or memory utilization on routers/switches
  • Bandwidth saturation (e.g., WAN link exceeds 90% utilization)
  • Device unreachable (ICMP ping failure)
  • Temperature or power supply anomalies on enterprise switches

Alert actions include email notifications, SMS (via email-to-SMS gateways), syslog messages, or executing external scripts (e.g., bouncing a port).

3. Network Performance Monitor (NPM)

NPM is the core SolarWinds module for monitoring network devices. It provides:

  • Availability monitoring (ping, SNMP status)
  • Bandwidth utilization graphs (real-time and historical)
  • Packet loss, latency, and jitter monitoring via IP SLA
  • Wireless network monitoring (AP status, client counts)
  • Custom dashboards and reporting

4. Server & Application Monitor (SAM)

SAM extends SolarWinds beyond networking into server and application monitoring. It can monitor Windows/Linux servers, databases (MySQL, SQL Server), web services, and custom applications. SAM uses WMI, PowerShell, SSH, and SNMP to gather metrics.

5. Network Topology Mapper

SolarWinds automatically discovers network devices using Layer 2 and Layer 3 discovery protocols (CDP, LLDP, ARP tables). It generates dynamic network topology maps that update as the network changes. This is invaluable at Matrix for visualizing the entire infrastructure from core to client edge.

6. Orion Platform Architecture

SolarWinds runs on the Orion platform, which consists of:

  • Orion Web Console: The central web interface for configuration, monitoring, and reporting
  • Polling Engines: Dedicated servers (Additional Pollers) that distribute the polling load
  • SQL Server Database: Stores all configuration, historical performance data, and alerts
  • Additional Modules: NTA (NetFlow Traffic Analyzer), IPAM, UDT (User Device Tracker), and more

Configuring SNMP on Routers for SolarWinds

For SolarWinds to poll a device, SNMP must be enabled and configured on the target router or switch. Below are sample configurations for Cisco IOS and MikroTik RouterOS — both commonly found at Matrix Telecom.

Cisco IOS SNMP Configuration

! Enable SNMPv2c with a read-only community string
!
snmp-server community matrix_ro RO
snmp-server community matrix_rw RW
snmp-server location "Matrix_CORE_SiteA"
snmp-server contact "noc@matrixtelecom.cm"
snmp-server enable traps snmp linkdown linkup
snmp-server host 192.168.10.50 version 2c matrix_ro
!
! Restrict SNMP access to the SolarWinds poller only
access-list 10 permit 192.168.10.50
snmp-server community matrix_ro RO 10

MikroTik RouterOS SNMP Configuration

/snmp community set [find] address=192.168.10.50/32
/snmp community set [find] name=matrix_ro
/snmp set enabled=yes contact="noc@matrixtelecom.cm" \
  location="Matrix_ClientSite_01" trap-community=matrix_ro \
  trap-version=2
/snmp community add name=matrix_ro address=192.168.10.50/32

Practical Example at Matrix Telecom Yaoundé

Matrix Context: Monitoring Client CPEs and Core Infrastructure

Matrix Telecom manages hundreds of client CPEs (router/AP combos) across Yaoundé. Each CPE is configured with a unique IP address and SNMP community string. The SolarWinds Orion NPM polls each CPE every 5 minutes for:

  • Availability: ICMP ping check — if a CPE goes offline, an alert is sent to the NOC within 60 seconds
  • Bandwidth Usage: Per-interface traffic graphs for the WAN port (to client) and LAN port (to customer equipment)
  • Signal Strength (Wireless CPEs): Using vendor-specific MIB OIDs for RSSI and SNR values
  • Uptime: Device uptime via sysUpTime OID (1.3.6.1.2.1.1.3.0)

The NOC team uses a large-screen dashboard showing a heat map of client CPE status by arrondissement (neighborhood), enabling rapid response to outages. Weekly reports are generated for the operations manager showing average bandwidth utilization and top talkers per zone.

Tools Used

SolarWinds Orion Web Console
Access: https://solarwinds.matrixtelecom.cm (internal)
Purpose: Central interface for all monitoring, alert configuration, dashboard creation, and reporting.

  • Acknowledging alerts: Click the bell icon, select alert, click Acknowledge.

Purpose: Monitor Matrix's internal servers (DHCP, DNS, billing, RADIUS).
Usage: SAM templates are available for Windows Server, Linux (SSH), MySQL, and Apache. Assign templates to nodes for automatic monitoring of services.
SolarWinds NPM (Network Performance Monitor)
Purpose: Core module for all network device monitoring — bandwidth, CPU, memory, interface errors.
Usage: NPM automatically calculates baseline thresholds after 30 days of data collection. Custom threshold profiles can be applied per device group.

Tips for the Intern

Intern Tip:
  • Always verify that SNMP is reachable from the SolarWinds poller before adding a node. Use snmpwalk -v2c -c matrix_ro 192.168.x.x from a Linux jump host to test.
  • When adding a new client CPE, group it by arrondissement or client type (residential vs. business). This makes dashboard filtering and reporting much easier.
  • Spend time learning the Orion "UnDP" (Universal Device Poller). It allows you to poll any custom OID — useful for vendor-specific metrics like signal strength or radio temperature.
  • Do NOT set polling intervals lower than 5 minutes for large deployments — you can overwhelm the polling engine and the devices being monitored, especially if you have 500+ CPEs.
  • Use the "Network Atlas" feature to create geographical maps of the Matrix network in Yaoundé. Import a map background and place nodes by neighborhood.
  • If an alert fires repeatedly, investigate and fix the root cause rather than disabling the alert. Disabled alerts lead to blind spots.
  • Learn the Orion API (REST and PowerShell) — you can automate node additions, bulk configuration changes, and report generation.

Common SNMP OIDs for Network Monitoring

.1.3.6.1.2.1.1.3.0        — sysUpTime (device uptime in hundredths of seconds)
.1.3.6.1.2.1.1.5.0        — sysName (device hostname)
.1.3.6.1.2.1.2.2.1.2      — ifDescr (interface description)
.1.3.6.1.2.1.2.2.1.6      — ifPhysAddress (MAC address)
.1.3.6.1.2.1.2.2.1.10     — ifInOctets (bytes received)
.1.3.6.1.2.1.2.2.1.16     — ifOutOctets (bytes sent)
.1.3.6.1.2.1.2.2.1.20     — ifOperStatus (1=up, 2=down)
.1.3.6.1.2.1.25.3.3.1.2   — hrProcessorLoad (CPU %)
.1.3.6.1.2.1.25.2.3.1.6   — hrStorageUsed (storage used in bytes)

Best Practices for SolarWinds Deployment

  • Use dedicated polling engines: For networks with 1000+ nodes, deploy Additional Pollers to distribute the load.
  • Implement role-based access: Restrict alert acknowledgment and node configuration to senior NOC staff only.
  • Set maintenance windows: Use SolarWinds maintenance schedules to suppress alerts during planned maintenance.
  • Monitor the monitor: Configure Orion to monitor its own health — database size, polling engine queue depth, and disk space.
  • Back up the Orion database: Schedule nightly SQL Server backups. A corrupt database means losing all historical data.
  • Use custom properties: Tag nodes with custom properties like "ClientName", "CircuitID", "BandwidthPlan" for powerful filtering and reporting.
